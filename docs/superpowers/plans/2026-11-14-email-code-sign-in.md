# Email Code Sign-in Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Guests sign in to locked projects with their email and a 6-digit code sent by email, and stay signed in until Kiran ends their access.

**Architecture:** The guest-pass cookie, the proxy gate and the console stay. The guest's word-password becomes a random server-side pass key that only signs the cookie; a hashed, short-lived sign-in code on the `guests` row is what the visitor proves. Two new server actions (start sign-in, verify code) feed one client card that replaces the password form on the teaser and the showcase unlock page. Emails get one HTML template.

**Tech Stack:** Next.js 16 server actions, Drizzle + Neon (PGlite in tests), zod, Resend HTTP API, shadcn `input-otp`, vitest + testing-library.

**Spec:** `docs/superpowers/specs/2026-11-14-email-code-sign-in-design.md`

All paths below are relative to `apps/portfolio/` unless they start with `docs/` or are the root `CLAUDE.md`. Run tests from `apps/portfolio` with `npx vitest run <file>`.

## Global Constraints

- Migrations are additive only (no drops, no renames): `drizzle/0004_sign_in_codes.sql`.
- Code: 6 digits, 10 minutes, 5 wrong tries, 60 s between sends, 5 sends per IP per 15 min.
- Guest-pass cookie `maxAge` 365 days; fallback `showcase-access-<slug>` cookie stays a session cookie.
- No new env vars. HMAC secret is `ADMIN_SESSION_SECRET`, through `hmac()` in `src/lib/access/crypto.ts`.
- shadcn components only; semantic tokens only; `&apos;` in JSX text; named exports for helpers, default exports for components.
- Every commit message ends with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`. No `Co-Authored-By` lines beyond that one.
- Branch `feat/email-code-sign-in` off `staging`. The PR targets `staging`, never `main`.

## Review Focus

1. Email case and spaces: `Ada@Example.com ` must find the guest `ada@example.com` in both start and verify (test in Task 5).
2. A code typed after a second code was requested must fail: only the latest code works (Task 5).
3. A guest paused between asking for the code and typing it must be refused at verify (Task 5).
4. A visitor who lands with `?email=` prefilled but types a different email in "Use a different email" must get a code for the typed one, not the prefilled one (Task 9: the form field, not a hidden input, carries the email).
5. `next` from the email button, like `next` from the form, must never leave the project (Task 3 keeps the existing `safeNext` tests and Task 7 reuses `safeNext`).
